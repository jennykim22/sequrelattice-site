seQure Lattice

양자컴퓨터가 나와도
열리지 않는 대화 Messages a quantum
computer can’t open

NIST 양자내성암호 표준을 실제 메신저에 적용한 안드로이드 앱입니다. 서버에는 암호문만 남고, 복호화 키는 각자의 기기 밖으로 나가지 않습니다. An Android messenger built on NIST’s post-quantum cryptography standards. The server stores only ciphertext, and decryption keys never leave each user’s device.

배경WHY

오늘 나눈 대화가 15년 뒤에 열린다면 What if today’s messages are opened 15 years from now?

지금 웹과 메신저에서 쓰는 공개키 암호는 큰 수의 소인수분해나 이산로그 문제를 풀기 어렵다는 데 기대고 있습니다. 양자컴퓨터는 바로 이 계산을 빠르게 해냅니다. The public-key cryptography behind today’s web and messengers relies on the difficulty of factoring large numbers or computing discrete logarithms. A quantum computer can do exactly those calculations quickly.

양자컴퓨터가 아직 없다고 안심할 수는 없습니다. 오늘 오가는 암호문을 모아 두었다가 나중에 한꺼번에 푸는 공격이 가능하기 때문입니다. 오래 지켜야 할 비밀일수록 지금부터 대비해야 합니다. Not having a quantum computer yet is no reason to relax. An attacker can collect encrypted traffic today and decrypt it later — “harvest now, decrypt later.” The longer a secret needs to last, the sooner you need to prepare.

NIST는 2024년에 이를 대체할 표준을 확정했습니다. 하지만 표준을 실제 메신저에 녹여 넣는 일은 또 다른 문제입니다. 암호 알고리즘보다 키를 언제 만들고, 언제 폐기하고, 어떻게 전달하느냐가 훨씬 까다롭습니다. 이 프로젝트는 그 과정을 직접 부딪쳐 본 기록입니다. NIST finalized replacement standards in 2024. But fitting those standards into a real messenger is a separate problem. The hard part isn’t the algorithm itself — it’s deciding when to create keys, when to discard them, and how to distribute them. This project is a record of working through exactly that.

구조STRUCTURE

하나의 앱, 두 가지 버전 One app, two versions

키 교환 계층을 제외한 코드는 모두 같습니다. 두 브랜치의 차이는 암호 관련 파일 10개뿐입니다. Everything except the key-exchange layer is identical. The two branches differ in just ten cryptography-related files.

ver1-full-security

검증된 라이브러리로 구현 Built on a vetted library

BouncyCastle이 제공하는 ML-KEM-768을 그대로 사용합니다. 부채널 공격 대응과 상수 시간(constant-time) 연산이 적용된 검증된 구현으로, 실사용에는 이 버전이 적합합니다. Uses BouncyCastle’s ML-KEM-768 as is. It’s a well-tested implementation with side-channel protections and constant-time operations — the version to use in practice.

ver2-kem-from-paper

논문을 보고 직접 구현 Implemented from the paper

CRYSTALS-Kyber 논문의 Algorithm 1~5를 외부 라이브러리 없이 구현했습니다. 다항식 곱셈은 일부러 NTT 대신 교과서식 곱셈(schoolbook multiplication)으로 작성해, 연산 과정이 코드에 그대로 드러나도록 했습니다. Implements Algorithms 1–5 of the CRYSTALS-Kyber paper with no external library. Polynomial multiplication deliberately uses the schoolbook method instead of NTT, so every step of the computation stays visible in the code.

표준을 쓸 줄 아는 것과 이해하는 것은 다르다고 생각했습니다. 직접 구현해 보니 부동소수점을 쓰지 않는 이유, 복호화에 실패해도 실패했다고 드러내지 않는 이유처럼 설계 하나하나에 담긴 의도가 보이기 시작했습니다. 덕분에 라이브러리를 쓸 때도 내가 무엇을 믿고 쓰는지 알게 되었습니다. I believe knowing how to use a standard and understanding it are two different things. Building it myself revealed the intent behind each design choice — why it avoids floating-point arithmetic, why a decryption failure isn’t reported as a failure. Now, when I use a library, I know what I’m trusting.

설계DESIGN

키를 다루는 방식 How keys are handled

1:1 대화One-to-one chats
메시지를 보낼 때마다 새 키를 만들고, 이전 키는 바로 삭제합니다. 또 말하는 사람이 바뀔 때마다 새로운 키 교환을 더해, 기기가 한 번 탈취되더라도 이후의 대화는 다시 안전해집니다. A new key is created for every message, and the previous key is deleted immediately. Each time the conversation changes direction, a fresh key exchange is mixed in, so even if a device is compromised once, later messages become secure again.
그룹 대화Group chats
1:1 방식은 두 사람이 메시지를 주고받아야 작동하므로, 여러 명이 참여하는 방에는 그대로 쓸 수 없습니다. 그래서 멤버마다 자신의 발신용 키 체인을 만들어 다른 멤버에게 나눠 줍니다. 멤버가 들어오거나 나갈 때, 그리고 24시간 또는 메시지 500건마다 체인을 새로 만들어 키가 노출될 수 있는 구간을 짧게 끊습니다. The one-to-one scheme depends on a back-and-forth between two people, so it doesn’t work for groups. Instead, each member creates their own sending chain and shares it with the others. Chains are regenerated whenever someone joins or leaves, every 24 hours, and every 500 messages, keeping the window of any exposed key short.
상대 확인Verifying contacts
서버가 전달하는 공개키를 그대로 믿지 않습니다. 처음 받은 공개키의 지문(fingerprint)을 기기에 저장해 두고, 이후 값이 바뀌면 통신을 멈춥니다. 처음부터 가짜 키를 받은 경우에는 두 사람이 서버를 거치지 않는 경로로 안전번호를 직접 비교해 확인합니다. Public keys supplied by the server aren’t trusted blindly. The fingerprint of the first key received is stored on the device, and communication stops if it ever changes. If the key was fake from the start, the two users catch it by comparing safety numbers over a channel that doesn’t go through the server.
서버의 역할The server’s role
서버는 암호문을 잠시 보관했다가 전달하고, 수신이 확인되면 삭제합니다. 대화 기록의 원본은 각 기기의 암호화된 로컬 DB에만 있으며, 계정마다 다른 키로 잠겨 있습니다. The server holds ciphertext briefly, delivers it, and deletes it once delivery is confirmed. The authoritative chat history lives only in each device’s encrypted local database, locked with a different key for each account.

안드로이드 앱은 Kotlin과 Jetpack Compose로, 서버는 Spring Boot와 PostgreSQL로 만들었습니다. 실시간 메시지 전달에는 WebSocket 기반의 STOMP를 사용하고, AWS EC2에 Nginx를 리버스 프록시로 두어 배포했습니다. The Android app is built with Kotlin and Jetpack Compose, and the server with Spring Boot and PostgreSQL. Real-time delivery uses STOMP over WebSocket, deployed on AWS EC2 behind an Nginx reverse proxy.

한계LIMITS

하지 않은 것 What this project doesn’t do

보안 제품에서는 무엇을 했는지보다 무엇을 하지 않았는지가 더 중요할 때가 많습니다. 현재 알고 있는 한계를 솔직하게 밝혀 둡니다. With security software, what it doesn’t do often matters more than what it does. These are the limitations I know of.

외부 보안 감사를 받지 않았습니다. 알고리즘은 NIST 표준을 따르지만, 이를 조합한 방식은 검증을 받지 않았습니다. No external security audit. The algorithms follow NIST standards, but the way they are put together has not been independently reviewed.
첫 연결 시점에는 여전히 속을 수 있습니다. 서버가 처음부터 가짜 키를 건네면, 두 사람이 안전번호를 직접 비교하기 전까지는 알아챌 수 없습니다. 이를 막으려면 발급된 키를 공개 로그에 기록하는 키 투명성(Key Transparency)이 필요하지만, 아직 구현하지 않았습니다. The first connection can still be spoofed. If the server hands out a fake key from the very first lookup, there’s no way to notice until the two users actually compare safety numbers. Preventing this requires key transparency — recording issued keys in a public log — which is not yet implemented.
서버는 누가 누구에게 보냈는지 알 수 있습니다. 메시지 내용은 볼 수 없지만, 누가 누구와 언제 대화했는지는 드러납니다. The server knows who messaged whom. It can’t read message contents, but it can see who talked to whom, and when.
직접 구현한 KEM은 학습용입니다. 비밀값에 따라 연산 시간이 달라지지 않도록 하는 상수 시간 처리를 하지 않아, 타이밍 부채널 공격에 취약합니다. 실제로 사용하려면 라이브러리 기반의 ver1을 권장합니다. The hand-built KEM is for learning only. It isn’t constant-time, so its running time depends on secret values, leaving it open to timing side-channel attacks. For real use, choose ver1, which relies on the library.
이 프로젝트는 학습과 포트폴리오를 위해 만들었습니다. 정말로 비밀을 지켜야 하는 대화에는 Signal처럼 오랫동안 보안 감사를 거쳐 온 도구를 사용하시기 바랍니다. This project was built for learning and as a portfolio piece. For conversations that truly need to stay private, please use a tool like Signal that has been audited over many years.
